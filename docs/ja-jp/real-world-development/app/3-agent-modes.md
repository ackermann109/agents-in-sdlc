プロジェクトに小さな機能を追加しました。大きな変更には、より確実なプロセスが必要です。GitHub Copilot app は組織の既存の開発フローに沿って作業できます。このレッスンから数回にわたり、Issue から新機能を実装し、コードが有効で動作が期待どおりであることを確認して、最終的にプロジェクトにマージする、一般的なエージェント主導の開発プロセスを実践します。

> [!NOTE]
> 機能の作業を続ける間、同じセッションを使います。通常は作業対象のファイルの種類ごとに異なるセッションや PR を使いますが、ここでは主な概念に集中するため手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub Issue からエージェント セッションを開始します。
- **Plan** モードで要件を決めます。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザー キャンバスで機能を手動で検証します。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の `quality-checks` スキルを調整し、MCP による検証を追加して QA エージェントを作成し、機能 PR を作成します。

## シナリオ

Tailspin Toys のカタログが増え、訪問者はカテゴリと publisher でゲームを絞り込む必要があります。バックログの Issue には機能が記載されていますが、カテゴリの組み合わせ方など、コーディング前に合意が必要な詳細があります。Plan モードで決定し、範囲を明確にしてから Autopilot に実装を許可します。

## 背景

AI コーディング エージェントを開発フローに導入しても、基本は変わりません。一般的な開発フローは次のとおりです。

1. 必要な作業の詳細が記載された Issue を開きます。
2. 実装する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 詳細な手順はチームや組織によって異なりますが、多くの場合は上記の流れを基にしています。

標準的なアプローチに従うことで、AI が生成したコードが要件を満たし、手書きのコードと同じレビューを受けていることを確認できます。

## セッション モード

**セッション モード**は、エージェントに与える自律性を決めます。プロンプト フィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: 開発者とエージェントが協力します。エージェントは変更を提案し、続行する前に入力を待ちます。
- **Plan**: エージェントが先に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律的にコードを書き、テストを実行して、入力を待たずに反復します。

Plan モードで始めて計画をレビューし、その後 Autopilot で実装します。

## Issue からセッションを開始する

開始する前に、星評価の PR がマージ済みで、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリ フォルダーを選び、リポジトリ上部のナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる Issue なので、新しく作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

   ![GitHub Copilot app の Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード選択メニューから **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行させます。自分のターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョン管理ツールの設定を確認し、アプリを完全に終了してから再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を検出できないという理由だけで再インストールしないでください。

## 絞り込み機能を計画する

計画を立てると、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能リクエストをすでに把握しています。次のプロンプトを送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を Issue の受け入れ条件と照らし合わせます。カテゴリと publisher による絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリの組み合わせや、ゲームが見つからない場合の動作など、不明確な点を話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。絞り込みの実装とテストに範囲を絞り、品質ワークフローが完了してから PR を作成します。承認前に計画の修正を依頼し、後の検証のために Issue の URL と合意内容を手元に控えます。

## Autopilot を明示的に承認する

計画に問題がなければ、**Approve and implement this plan** または使用中のバージョンにある同等の選択肢を選びます。承認によってモードが自動的に切り替わると決めつけず、現在のモードを確認します。モード表示が **Autopilot** になっていることを確認します。

Copilot は、計画に沿ってコードを生成してテストを実行し、実装を進めます。

> [!NOTE]
> 承認すると実装がすぐに始まる場合があるため、先に計画をレビューしてください。依存関係が不足している、またはポートが競合していると報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。自分で起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードは、他のコードと同様にマージ前にレビューします。

1. **Changes** を開き、絞り込みの実装とテストを確認します。
2. 複数カテゴリと publisher の組み合わせも含め、結果を Issue と承認した追加要件に照らし合わせます。変更が既存のリポジトリの指示に従っていることも確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、影響するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカル サーバーを再利用できます。以前のレッスンではなく、この worktree のサーバーがテスト対象であることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くか確認します。アプリを起動し、ブラウザー キャンバスでサイトを開きます。

1. 次のプロンプトでアプリを起動し、ブラウザー キャンバスを開くよう依頼します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. アプリが起動し、Copilot app 内にブラウザー ウィンドウが開くまで待ちます。
3. カテゴリを選択し、結果が一致することを確認します。フィルターを解除して publisher を選び、その publisher のゲームが表示されることを確認します。
4. カテゴリと publisher を組み合わせ、結果を Issue と承認済みの計画と比較します。複数カテゴリに対応する場合は、合意した組み合わせ動作を確認します。
5. 一致するゲームがない組み合わせを試して空の状態を確認します。フィルターを解除またはリセットし、一覧全体が戻ることを確認します。
6. 終了したら、次のプロンプトでこのセッションが起動した開発サーバーを停止します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンに向けてセッションを保持する

絞り込み PR はまだ作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はカスタム指示を絞り込みコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で PR を作成してマージします。開発サーバーを停止した後、セッションはそのままにしておき、次のレッスンで再開します。
